# H2：KV 容量与碎片检查

状态：两个独立 GPU 模型进程与[审计](audit.json)全部通过。
这轮回答分配容量、空洞复用与跨页正确性，不报告吞吐，也没有测得最大服务并发。
配置、复现与严格边界见[实验协议](../../../docs/h2_kv_capacity_protocol.md)。

## 相同 896 MiB KV 预算，谁能放下更多当前 KV？

固定 BF16、TP=1、256-token 页和 1024-token 窗口。每 token 的 K+V 为 112 KiB，
池共 8192 个 token 槽。表中数字是无共享条件下的分配请求数，不是同时生成请求数。

| 每请求当前 KV tokens | 固定预留完整窗口 | 按需连续、精确 token（CPU 参考） | 按需分页 |
|---:|---:|---:|---:|
| 128 | 8 | 64 | 32 |
| 256 | 8 | 32 | 32 |
| 257 | 8 | 31 | 16 |
| 512 | 8 | 16 | 16 |
| 768 | 8 | 10 | 10 |
| 1024 | 8 | 8 | 8 |

分页对固定窗口减少未来预留，但不是总比精确连续分配省空间。257-token 请求需要
两页，单请求浪费 255 个 token 槽；这一容量点 16 个请求合计页尾浪费 4080 槽、
446.25 MiB。128-token 点也有半页浪费。满 1024-token 时两者没有容量优势。
不要把“相对固定预留最多四倍”转述为“对任意连续缓存都四倍”或吞吐四倍。

## 外部空洞与增长是另外两个问题

同一初态下申请 16 个 512-token 请求，释放偶数编号后，总空闲 4096，但每个连续
空洞只有 512。新申请 768 时，CPU 连续 first-fit 拒绝；上游分页分配器接受，取得
真实页号 `[1, 0, 5]`。GPU 对这些非连续页的全部元素写入/读回哨兵，其他空闲页仍为
NaN。固定窗口放不下初始 16 个请求，因此没有拿不同初态作空洞对照。

增长小例中，第一个 256-token 请求扩到 257，连续参考需要搬到新位置，逻辑上应
复制原 256-token KV；分页保留旧页，只追加一页。这是复制需求，不是实测带宽或耗时。
连续参考没有全池 compaction；不同搬移策略可能改变是否能接纳，不能把这例当成
所有连续分配器都无法处理的结论。

## GPU 真实检查

两侧使用同一个模型/attention/Decode Graph，仅改变预留与页映射策略：

- 12 个同长度容量点，加 1 个分页空洞复用点，真实 GPU tensor 全元素哨兵隔离通过。
- 两侧 KV tensor 均为 `[2,28,32,256,8,128]`，896 MiB。逻辑分配前后设备 tensor
  指针不变，模型进程 PyTorch allocated 均保持 2,169,669,120 bytes。
- 相同八个 128-token prompt，各执行 132 个 teacher-forced 输出 token。最后一个
  输出还未写入缓存，因此最后一次 forward 对应 259 个 KV tokens。
- 两侧 1056 个全词表 BF16 向量全部 exact；最大绝对误差为 0。独立审计重新读取并
  核对完整保存张量，不能仅凭 JSON 中的 pass 字段判定。
- KV 先填 NaN，所有 logits、检查点的有效 KV 均有限；结束后全部页引用与队列清空。

| 当前 KV tokens/请求 | 固定预留已拥有页数 | 分页已拥有页数 | 第一个请求页表：固定 / 分页 |
|---:|---:|---:|---|
| 128 | 32 | 8 | `[0]` / `[0]` |
| 256 | 32 | 8 | `[0]` / `[0]` |
| 257 | 32 | 16 | `[0,1]` / `[0,8]` |
| 259 | 32 | 16 | `[0,1]` / `[0,8]` |

固定预留的未来页保存在 adapter 私有映射中，不提前暴露给 `seq.block_table`，否则
上游 Decode 的 `block_table[-1]` 写入会指向未来页。两侧都仍是 paged attention，
不是连续 attention kernel 与分页 kernel 的性能对照。
